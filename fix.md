## Issue 1 — Regenerating weeks/team does not regenerate the budget/financial

**Reported:** If we regenerate the timeline (weeks) or the team, the budget/financial estimation should be
regenerated accordingly. Example: a proposal has **24 weeks**; I regenerate it to **10 weeks**, but the
budget stays at the 24-week cost. Anything connected to the budget/financial should change too.

### Root cause

There are **two independent money computations**, and the single-block regenerate updates neither of the
visible ones:

1. **Two separate sources of "money" that never share a source of truth:**
   - **Proposal `financial` block** (agency template only) ← `decide.budget` = *per-phase team weekly × weeks*
     ([engine.service.ts:325](backend/src/modules/generation/engine/engine.service.ts#L325), computed in
     [decide.service.ts](backend/src/modules/generation/engine/decide.service.ts)).
   - **Budget tab** (the `Budget` entity, all templates) ← `generateBudget()` = a *separate AI call* that
     returns department/role/**days**, priced by the rate card
     ([generation.service.ts:393](backend/src/modules/generation/generation.service.ts#L393) →
     `budgets.applyGeneratedPlan`). Global/Local put the money **only** here (no `financial` block).

2. **`regenerateBlock` swaps only ONE block and discards the fresh, consistent budget**
   ([generation.service.ts:214‑239](backend/src/modules/generation/generation.service.ts#L214)):
   - It re-runs the **whole engine** (`engine.generate`), which produces a fresh, internally-consistent set
     of decisions — new timeline, new team, new financial — but then swaps **only the target block** of the
     same type back into the stored doc (line 228: `doc.blocks[idx] = { ...replacement, id: blockId }`).
   - So when a money-coupled block is regenerated (e.g. `timeline`, `teamAllocation`, `workApproach`):
     - The `financial` block keeps its **old** numbers (never swapped unless the financial block itself is
       the target).
     - Only `internalCalc` (the hidden 💡 verify breakdown) is refreshed
       (line 233, for `financial`/`teamAllocation`/`workApproach`) — **not** the visible financial rows.
   - The fresh run's consistent financial is **thrown away**.

3. **The Budget tab is never regenerated by `regenerateBlock`.** There is no `generateBudget` /
   `applyGeneratedPlan` call inside it (verified). The `Budget` entity is only (re)built by
   `generateDocument` (full generate) and `regenerateBudget` (the manual "Regenerate budget" button). So
   for **Global/Local** (money lives in the tab) regenerating the timeline leaves the tab at the old-weeks
   cost, and for **Agency** the tab is stale too.

4. **Secondary — no deterministic "weeks" target.** Only *money* targets are parsed
   (`parseBudgetTargetCents`). "Regenerate into 10 weeks" is passed to the engine as a soft prompt hint, so
   the new timeline is an LLM guess, not exactly 10 weeks. (Contrast the deterministic
   `DecideService.retargetBudget` used for money targets.)

5. **Edit path has the same gap.** Inline-editing the timeline weeks or the team via the block editor calls
   `updateBlock` ([proposal.service.ts](backend/src/modules/proposal/proposal.service.ts)) which just merges
   the patch into that one block — it does not recompute the financial block or the budget tab.

### Solution plan

Goal: when a money-coupled block is regenerated (or edited), **everything connected to the money updates
together and stays mutually consistent** — the displayed timeline, team, the `financial` block, and the
Budget tab.

1. **Define the "financially-coupled" block set:** `workApproach`, `teamAllocation`, `timeline`, `financial`.

2. **In `regenerateBlock`, when the target is in that set, propagate the whole fresh run instead of one block:**
   - Swap **all coupled blocks that exist in the doc** from the same `fresh` result (so the shown team /
     timeline / financial all come from one decision set — no mismatch), keeping each block's `id` + position.
   - **Regenerate the Budget tab from the same pass** so the tab matches: call `generateBudget(...)` (or a
     shared helper) right after the swap, using the same `brief`/`meta`/`instructions`. Best-effort, wrapped
     in try/catch like `generateDocument` does.
   - Keep the existing `setInternalCalc` refresh.
   - Non-coupled blocks (e.g. `scope`, `comparables`) keep today's single-block behaviour.

3. **(Recommended) Make the two money sources agree.** Today the `financial` block and the Budget tab are two
   different AI computations that can диverge. Decide one of:
   - **(a)** Derive the Budget-tab lines from the engine's `decisions` (per-phase teams) instead of a second
     AI call — one source of truth; regenerate-consistency becomes automatic. (Requires `engine.generate` to
     also return `decisions`, which it currently does not — it returns `{ doc, usage, diagnostics,
     internalCalc }`; add `decisions` to the return.)
   - **(b)** Keep two computations but always regenerate both together (item 2) and document that they are
     independent estimates. Lower effort, but they can still differ in totals.
   - *Preference:* (a) — single source of truth removes a whole class of "numbers don't match" bugs.

4. **(Recommended) Deterministic weeks target.** Add a `parseWeeksTarget(instructions)` (mirroring
   `parseBudgetTargetCents`) and a `DecideService.retargetWeeks(decisions, totalWeeks)` that scales the phase
   plan to hit exactly N weeks, then recomputes the phase-wise budget from it (mirroring `retargetBudget`).
   Wire it through `engine.generate({ ..., weeksTargetCents/weeksTarget })`. This makes "regenerate into 10
   weeks" land on 10 weeks and the budget follow exactly.

5. **(Follow-up) Edit path.** After `updateBlock` on a coupled block (weeks/team edited by hand), recompute
   the `financial` block + Budget tab from the current values. This is harder than regenerate because the
   **per-phase team detail lives in `internalCalc`, not the client-facing blocks**, so a pure
   recompute-from-visible-blocks can't see per-phase teams. Options: recompute from `internalCalc` + the
   edited weeks, or (cleanest) fold this into the single-source-of-truth model from item 3(a). Flag for a
   later pass; not required to satisfy the reported regenerate case.

### Files in scope
- `backend/src/modules/generation/generation.service.ts` — `regenerateBlock` (coupled-group swap + budget-tab
  refresh); `parseBudgetTargetCents` sibling `parseWeeksTarget`.
- `backend/src/modules/generation/engine/engine.service.ts` — expose `decisions` from `generate`; thread a
  weeks target.
- `backend/src/modules/generation/engine/decide.service.ts` — `retargetWeeks` (+ possibly derive budget-tab
  lines from decisions for single source of truth).
- `backend/src/modules/budget/budget.service.ts` — `applyGeneratedPlan` reused if deriving the tab from decisions.

### Verification (when implemented)
- Regenerate the `timeline` of a Global/Local proposal to fewer weeks → the **Budget tab total scales down**
  proportionally and the shown team/timeline match the tab.
- Regenerate `teamAllocation` (fewer/more people) → the `financial` block (agency) **and** the Budget tab
  both change; the 💡 verify math reconciles to the new total.
- Regenerate with "make it 10 weeks" → timeline shows exactly 10 weeks and the budget reflects 10 weeks.

## Issue 2 — Additional requirements are not understood first / given top priority  ✅ FIXED (2026-08-17)

**Resolution applied:**

  requirements and the uploaded document's `sourceText` can never overwrite each other.

  saves the paste box to `additionalRequirements` (not `sourceText`). Readiness/query-generation and the

- `buildEngineInput` assembles the effective brief in **priority order** with framing headers:
  `TOP-PRIORITY (typed requirements → project context)` → `ATTACHED DOCUMENT (supporting detail)` → Q&A →
  instructions; the header tells the model the priority inputs are authoritative and win on conflict, while
  the document must not be ignored (it supplies the detail).
- Step-2 label updated to "Additional requirements — top priority; shapes the proposal".
- **Verified:** uploaded a document (source_text 38,009 chars), then saved typed requirements → source_text
  unchanged, typed text stored separately (both preserved). Backend + frontend typecheck clean.

_Original diagnosis + expanded plan below._



**Reported:** When uploading a client brief, if we also write additional requirements, the system should
understand those additional requirements **first** and give them **top priority** when generating the
proposal and the budget.

### Root cause

There is no concept of "priority requirements" anywhere in the pipeline — the rep's typed text and the
uploaded document are flattened into one undifferentiated blob and fed to the AI with equal weight.

1. **Typed text + uploaded-file text are merged into one `source_text`.** When a file is attached, its
   extracted text is **appended** to `source_text` under a `--- filename ---` header
   ([requirement.service.ts:81‑86](backend/src/modules/requirement/requirement.service.ts#L81)). The rep's
   typed requirements and the client's document become one flat string with no "priority" marker.

2. **Step 2 has a single paste box, no dedicated "additional requirements" field.** The wizard stores the
   textarea as `source_text` via `upsertRequirement(leadId, brief.trim())`
   ([new-lead.tsx:137](frontend/app/pages/new-lead.tsx#L137)); files are uploaded separately and appended.
   So "additional requirements" == the same `source_text` the file text lives in — indistinguishable
   downstream.

3. **No prioritization in the effective brief.** `buildEngineInput` assembles
   `[briefBase, context, qna, instructions]`
   ([generation.service.ts:154‑161](backend/src/modules/generation/generation.service.ts#L154)) — the whole
   merged `source_text` is passed as one `briefBase` with no ordering or precedence.

4. **No prioritization in the prompts.** `UNDERSTAND_SYSTEM` ("extract structured facts… be specific to THIS
   brief") and `COMPOSE_SYSTEM` contain **no instruction** to weight the rep's additions above the attached
   document. A large uploaded brief can drown out short but important typed requirements.

5. **Adjacent data-loss risk (verify).** On step-2 continue, `upsert` sets `sourceText: dto.sourceText`
   (overwrite, not merge — [requirement.service.ts:56](backend/src/modules/requirement/requirement.service.ts#L56)).
   If a file was uploaded first (its text in `source_text`) and the textarea does not already contain that
   text, submitting the typed text can **overwrite/lose the file's extracted text**. The exact FE sync needs
   confirming, but the overwrite path exists.

### Solution plan

1. **Introduce a first-class "Additional / priority requirements" field**, stored **separately** from the
   file-extracted `source_text` (e.g. `requirement.priorityNotes`, or repurpose `lead.projectContext` as the
   explicit priority slot). Surface it as its own input on step 2 so it can never be buried or overwritten by
   file extraction.

2. **Place it at the TOP of the effective brief with an explicit precedence header** in `buildEngineInput`:
   order becomes `[PRIORITY header + additionalRequirements, briefBase (uploaded/extracted), context, qna,
   instructions]`. Header text, e.g.: *"TOP-PRIORITY REQUIREMENTS from the Riseup sales rep — read and apply
   these FIRST. Where they add to, refine, or conflict with the attached client brief below, THESE take
   precedence."*

3. **Teach the prompts to honor precedence.** Update `UNDERSTAND_SYSTEM`, the Decide prompt, and
   `COMPOSE_SYSTEM` to state that the rep's priority requirements override the attached brief on conflict,
   and that every priority requirement must be reflected in the Intent → scope → plan → budget.

4. **Understand-first (optional, robust):** have the Understand pass extract the priority requirements into
   dedicated Intent fields (e.g. `mustHave[]`, `constraints[]`) so Decide/Compose cannot silently drop them.

5. **Close the overwrite risk:** ensure uploading a file + typing additional requirements **merges** rather
   than replaces (keep file-extracted text separate from the typed priority field, so neither clobbers the other).

### Files in scope
- `frontend/app/pages/new-lead.tsx` — step 2: add a distinct "Additional / priority requirements" input; keep
  it separate from the uploaded-file text.
- `backend/src/modules/requirement/*` (entity, dto, `requirement.service.ts`) — persist priority notes separately.
- `backend/src/modules/generation/generation.service.ts` — `buildEngineInput`: priority-first ordering + header.
- `backend/src/modules/generation/engine/understand.service.ts` + `engine.service.ts` — precedence language in
  the Understand/Decide/Compose prompts; optional must-have extraction.

### Verification (when implemented)
- Upload a brief stating X; type an additional requirement that adds/changes a specific feature, tech, or
  constraint (different from the document) → the generated proposal **and** budget reflect the typed
  requirement, and where it conflicts with the document, the typed requirement wins.
- Upload a file, then type additional requirements, then continue → the file's extracted text is still present

### Update (2026-08-17) — CONFIRMED root cause + Project-context priority

Investigated the exact wizard data flow; the "adjacent risk" above is the **primary** bug, now confirmed:

- **Only ONE of {document, typed text} ever survives — they are never combined.**
  - The `brief` textarea starts empty and is **never preloaded** from the requirement
    ([new-lead.tsx:52,308](frontend/app/pages/new-lead.tsx#L52)) — it holds only what the user types this session.
  - `uploadBriefAttachment` returns only `{ parsed, extractedChars }`
    ([requirement.service.ts addAttachment response](backend/src/modules/requirement/requirement.service.ts#L94)),
    **not** the extracted text, so the UI cannot show/merge the document text into the textarea.
  - A file upload stores its text in `source_text` (append), but on **Continue**
    `if (brief.trim()) upsertRequirement(leadId, brief.trim())`
    ([new-lead.tsx:137](frontend/app/pages/new-lead.tsx#L137)) → `upsert` sets `sourceText: dto.sourceText`
    ([requirement.service.ts:56](backend/src/modules/requirement/requirement.service.ts#L56)) = **overwrites**
    with only the typed text. → **The document's extracted text is discarded** whenever the user also types.
    (If no text is typed, the document survives; if no document, the text survives — hence "only one part is read".)

- **Project context (step 3) is not prioritised either.** `lead.projectContext` is appended **after**
  `briefBase` in `buildEngineInput`
  ([generation.service.ts:156](backend/src/modules/generation/generation.service.ts#L156)) with no precedence —
  so it does not shape the foundational understanding.

**Required behaviour (from the report):**
1. Consider **both** the document and the typed requirements (never drop one).
2. When both exist, the **typed requirements take priority** and the **document is interpreted under that
   framing** (typed wins on conflict; document fills in supporting detail).
3. **Project context** is likewise prioritised as foundational project understanding.

**Expanded solution:**
1. **Store the three inputs in separate fields** so none can overwrite another:
   `documentText` (file extraction, current `source_text`), `additionalRequirements` (the typed priority text),
   and `projectContext` (already separate on the lead). `upsert` must only write the typed field, never clobber
   `documentText`. Fix the FE to save the textarea into `additionalRequirements` (not `source_text`).
2. **Build the effective brief in priority order with explicit framing headers** in `buildEngineInput`:
   `[TOP-PRIORITY REQUIREMENTS (typed)] → [PROJECT CONTEXT] → [ATTACHED CLIENT DOCUMENT] → [qna] → [instructions]`,
   with a header such as: *"The following TOP-PRIORITY requirements and project context come from the Riseup
   rep — read them FIRST and treat them as authoritative. Interpret the attached client document UNDER this
   framing; where the document conflicts, the priority requirements win."*
3. **Prompts** (`UNDERSTAND_SYSTEM`, Decide, `COMPOSE_SYSTEM`): honor precedence and require every priority
   requirement + context point to flow into Intent → scope → plan → budget.

**Extra files in scope (beyond Issue 2 base):**
- `backend/src/modules/requirement/{requirement.entity.ts, dtos, requirement.service.ts}` — add
  `additionalRequirements` (or repurpose a field); make `upsert` non-destructive to `documentText`.
- `frontend/app/pages/new-lead.tsx` — save the textarea to the new field; keep document + typed text both visible.

## Issue 3 — Regeneration prompt is not reflected / budget target not applied exactly

**Reported:** The regeneration prompt is not reflecting on the proposal. When I add a prompt and regenerate,
the system should understand and follow it, always prioritising the regeneration prompt and modifying the
budget accordingly. Example: a prompt to regenerate the budget to **10 lacs (₹10,00,000 / 1,000,000)** should
land **exactly** on that number.

> Related to Issue 1 (budget not regenerating with weeks/team) and Issue 2 (input prioritisation). The
> targeting mechanism exists but is wired to the wrong place.

### Root cause

1. **Exact budget targeting only touches the proposal `financial` block, never the Budget tab.**
   `DecideService.retargetBudget` scales `decisions.budget` (→ the `financial` block)
   ([decide.service.ts:239](backend/src/modules/generation/engine/decide.service.ts#L239)). It is invoked via
   `engine.generate({ budgetTargetCents })`. But:
   - **Global/Local** put the money **only in the Budget tab** (no `financial` block), so the target has
     nothing to act on — it is effectively **ignored**.
   - **Agency** has a `financial` block that hits the target, but the auto-generated **Budget tab** (a
     separate computation) diverges and does **not** hit it.

2. **`regenerateBudget` (the Budget-tab "Regenerate budget" button) does not parse or apply a target.** It
   passes the prompt to `generateBudget` as a soft hint only — verified: no `parseBudgetTargetCents`, no
   scaling ([generation.service.ts:360‑369](backend/src/modules/generation/generation.service.ts#L360)). So
   "regenerate the budget to 10 lacs" yields an LLM estimate, not the exact number.

3. **`generateBudget` has no deterministic target-scaler** (unlike `retargetBudget` for the financial block) —
   it prices the AI's resource plan and saves it as-is.

4. **The regen prompt is injected weakly and late.** It is appended to the **end** of the effective brief as
   `"Revision instructions from the sales rep:\n{prompt}"`
   ([generation.service.ts:158](backend/src/modules/generation/generation.service.ts#L158)) with **no
   precedence language** in the Understand/Decide/Compose prompts. So general (non-budget) prompts — "add a
   mobile app", "make the tone formal" — are weakly followed, buried after the whole brief. (Same mechanism as
   Issue 2.)

5. **Parser robustness gap.** `parseBudgetTargetCents` anchors on `to/at/under/around/…` but **not "in"**, so
   "budget **in** 10 lacs" relies on the "last money figure" fallback. It works for a lone number but is
   fragile when the prompt contains other numbers (e.g. "10 weeks and 10 lacs").

### Solution plan

1. **Apply exact budget targeting to the Budget tab.** In `regenerateBudget` **and** in `generateDocument`'s
   budget step, run `parseBudgetTargetCents(instructions)`; after `generateBudget` builds the priced lines,
   deterministically **scale to the target** via a new `retargetBudgetLines(lines, targetCents)` helper
   (mirror `retargetBudget`: `k = target/current`, scale each line's `days` by `k`, round, then nudge the
   largest line to close the rounding gap), then `applyGeneratedPlan`. Record a transparent note
   ("Scaled to your ₹10,00,000 target → …").

2. **Make the financial block and the Budget tab agree (ties to Issue 1).** Prefer a single source of truth
   (derive both from the same `decisions`), so one target hits both; otherwise run the same scaler on both so
   they can't diverge.

3. **Prioritise the regen prompt (ties to Issue 2).** Move the regen prompt to the **top** of the effective
   brief with a strong header ("TOP-PRIORITY revision instructions — apply these to the draft; they OVERRIDE
   the brief where they differ"), and add precedence language to the Understand/Decide/Compose prompts so
   general prompts are reliably applied.

4. **Harden the parser.** Add `in`, `make it`, `of` as anchors; keep lakh/lac/crore/k/m/thousand/million
   scaling; prefer the number nearest the budget/price keyword over "just the last number".

### Files in scope
- `backend/src/modules/generation/generation.service.ts` — `regenerateBudget` + `generateDocument` budget step
  (parse + scale to target); `parseBudgetTargetCents` (anchors/units); prompt-priority ordering in
  `buildEngineInput`.
- `backend/src/modules/budget/budget.service.ts` — new `retargetBudgetLines` (scale `days` to hit a total),
  used by `applyGeneratedPlan`/callers.
- `backend/src/modules/generation/engine/{understand,engine}.service.ts` — precedence language for the regen prompt.
- (Optional, Issue 1 overlap) `decide.service.ts` / `engine.service.ts` — single source of truth for money.

### Verification (when implemented)
- Budget-tab "Regenerate budget" with "10 lacs" → tab total lands at ~₹10,00,000 (± one line-day), for BDT
  and USD alike.
- Proposal regenerate with "budget 10 lacs" → both the `financial` block (agency) and the Budget tab hit the
  target and match each other.
- Non-budget regen prompt ("add offline mode", "make it more formal") → clearly reflected in the regenerated
  proposal.

## Issue 7 — Regeneration Overhaul (supersedes Issues 1 & 3) — the biggest issue

**Reported (consolidated):** Regeneration is "non-functional in output quality." Required behaviour:
1. **Budget is a spreadsheet ("budget sheet like Excel").** Changing **weeks** or **team members** — via
   regenerate **or** manual edit — must **deterministically recalculate** the budget against the rate card.
   Not guessing; straight arithmetic. Edit a week/member → budget updates, exactly like editing an Excel cell.
2. **Section-level feedback with highest priority + ripple.** For any section the user can give feedback; the
   regen prompt takes **top priority**, and if a change affects other parts it must propagate — e.g. **tech
   stack change → resource/role change → budget recalc against the sheet**.
3. **Client feedback** (after the proposal is sent) also feeds regeneration with **highest priority**.
4. **Budget limit → adapt.** If a budget limit is given, regeneration adapts **weeks/members to fit within it**
   (e.g. "10 lacs" → scale to exactly that), and any exception (e.g. "reduce weeks but budget stays high") is
   honoured per the prompt.
5. **Regeneration = same rigour as first generation.** Re-check everything; keep what's genuinely unaffected as-is;
   ensure the whole proposal stays aligned and wired up. Always give the user's prompt/feedback priority.
6. **UI:** under the "Regenerate proposal" prompt, add a small (~1 inch) **scrollable "what changed" summary**
   that appears after a regeneration completes (like Claude Code's post-task recap).

### Root cause (verified)

1. **No single source of truth for the plan.** Money is computed **twice by different mechanisms** that never
   reconcile:
   - Proposal `financial`/`timeline`/`teamAllocation` blocks ← `decide.service` (per-phase team × **weeks**).
   - Budget **sheet** (`Budget`/`Milestone`/`BudgetLine`) ← `generateBudget` (dept/role × **days**;
     `BudgetLine` has `units`, `days`, `dayRateCents` — **days-based**, [budget-line.entity.ts](backend/src/modules/budget/budget-line.entity.ts)).
   Two models (weeks vs days), two computations, stored separately → they can't stay in sync.

2. **Regeneration is block-scoped, not holistic.** `regenerateBlock` re-runs the engine but **swaps one block**
   and discards the rest ([generation.service.ts:214](backend/src/modules/generation/generation.service.ts#L214));
   no ripple (tech stack → team → budget), and the Budget sheet is never touched (Issue 1).

3. **Nothing recomputes on change.** Manual `updateBlock` just merges a patch — **no budget recompute**
   ([proposal.service.ts:153](backend/src/modules/proposal/proposal.service.ts#L153)). Changing weeks/members
   in the proposal does not touch the sheet. (The Budget **sheet** *does* recompute on its own edits via
   `computeBudget` — [budget.service.ts](backend/src/modules/budget/budget.service.ts#L145) — so the Excel
   engine exists, but only inside the isolated sheet.)

4. **Targeting hits the wrong representation** (Issue 3): `retargetBudget` scales only `decisions.budget`
   (financial block), never the sheet; `regenerateBudget` applies no target at all.

5. **Prompt/feedback are low-priority & non-deterministic** (Issues 2 & 3): the regen prompt is appended weakly
   to the brief; week/team/budget targets aren't parsed deterministically.

6. **No client-feedback channel into regeneration.** A `feedback.entity.ts` and `lead-comment.entity.ts` exist
   but are **not** fed into the generation brief with priority.

7. **No change summary** is produced by (re)generation.

### Solution plan (backend approach change — approved by user)

**Core idea — one canonical, deterministic "Delivery Plan" that both the proposal and the budget sheet derive
from.** Regeneration and manual edits mutate the Plan; a single pure calculator recomputes money. This makes
"weeks/members → budget" exact and Excel-like, and keeps proposal ⇄ sheet always in sync.

**1. Canonical Delivery Plan (single source of truth).**
   - Persist a `Plan`: `phases[{ name, weeks, team[{ role, seniority, units, dayRateCents }] }]` + currency +
     adjustments (contingency/discount/VAT). (This is exactly `decisions.phases` today — promote it to a stored,
     editable entity.)
   - **Both** the proposal blocks (`timeline`, `teamAllocation`, `financial`) **and** the Budget **sheet** are
     **derived** from the Plan. Reconcile weeks↔days: a role's `days = Σ(weeks of phases it's in) × 5`, so the
     existing days-based sheet becomes a *view* of the weeks-based Plan (no more divergence).

**2. One deterministic calculator (the "Excel").**
   - A single `computePlan(plan, rateCard, adjustments)` → per-phase + grand totals, used by the proposal, the
     sheet, and every recompute. Pure arithmetic against the rate card; never the LLM.

**3. Holistic, priority-driven regeneration.**
   - Regen prompt **and** client feedback go to the **top** of the brief as authoritative (reuse Issue 2's
     priority-block mechanism). Parse deterministic directives: **budget target** (₹10 lacs), **weeks target**
     (10 weeks), **team edits** (add/remove/adjust roles).
   - Apply deterministic directives directly to the **Plan**, then `computePlan` → budget follows exactly.
   - Preserve sections not implicated by the prompt/feedback; **ripple** dependent ones through the Plan
     (tech-stack change → team change → budget recompute). Re-verify the whole document is aligned (first-gen rigour).
   - Return a **structured change summary** (see 6).

**4. Budget-limit / weeks adaptation (deterministic).**
   - Generalise `retargetBudget` into a Plan-level solver: given a target total or week count, scale weeks and/or
     trim/adjust team to hit it (± rounding), operating on the canonical Plan so the sheet + proposal both reflect
     it. Record the trade-off in the summary/rationale. Honour explicit exceptions from the prompt.

**5. Manual-edit sync (Excel behaviour).**
   - Editing weeks (timeline) or team (teamAllocation) in the proposal, **or** editing the sheet, mutates the Plan
     → `computePlan` → both views update. `updateBlock` for coupled blocks must recompute (or route through the
     Plan). No AI, immediate.

**6. Client feedback channel.**
   - Persist client feedback (extend `feedback.entity`/lead-comment) with a "for regeneration" flag; include it in
     the priority block of the brief at top priority; regeneration applies it and marks it addressed.

**7. Regeneration summary UI + payload.**
   - (Re)generation returns a `changeSummary: { changed: string[], kept: string[], budgetDelta, notes }`.

## Issues 7 + 8 — COMBINED IMPLEMENTATION PLAN (Regeneration + daily-base budget)

  monthly = daily × `DAYS_PER_MONTH(20)` (= weeks × `WEEKS_PER_MONTH(4)` × 5). Monthly & hourly columns are never
  read for money — derived on display only.

_Original diagnosis below._



**Reported:** The cover invents a project name — it adds extra words that aren't in the requirement (e.g. a
plain brief becomes "… Digital Health Platform" / "… Clean Cooking & Carbon Platform"). The cover name should
**exactly** match the project name given in the requirement.

### Root cause

1. **The compose prompt explicitly asks the AI to invent a product name.**
   [engine.service.ts:240](backend/src/modules/generation/engine/engine.service.ts#L240):
   `'- coverProjectName: a short product name (e.g. "SkyLink Air Ticketing Platform")'`. The instruction and
   its example actively encourage adding descriptive words ("Platform", "Digital … Platform", etc.).

2. **The actual project title is never available to the engine.** `ProposalMeta` carries `client.name`
   (= `lead.company`) but **not** `lead.title` (the project name the rep entered in the wizard). `buildEngineInput`
   never passes it, so the cover cannot use it.

3. **The assemble step + fallback use only the invented name.**
   [engine.service.ts:288](backend/src/modules/generation/engine/engine.service.ts#L288):
   `projectName: c.coverProjectName`; fallback
   [engine.service.ts:259](backend/src/modules/generation/engine/engine.service.ts#L259):
   `data.coverProjectName || intent.domain || 'Proposed Platform'` — i.e. AI name → derived `domain` label →
   generic placeholder. The real title is nowhere in the chain.

### Solution plan

1. **Pass the real title into the engine.** Add `projectTitle` (or `title`) to `ProposalMeta` (backend
   `block.types.ts` + frontend `proposal.d.ts`) and set it from `lead.title` in `buildEngineInput`.

2. **Use the exact title as the cover `projectName`.** In assemble:
   `projectName: (meta.projectTitle?.trim() || c.coverProjectName)` — prefer the rep's/requirement's actual
   name verbatim; only fall back to the AI name when no title exists.

3. **Stop the invention in the prompt.** Change the `coverProjectName` instruction to: *"the EXACT project name
   as stated in the requirement/title — do NOT add descriptive words, taglines, or invent a product name."*
   Replace the "SkyLink Air Ticketing Platform" example with a plain, non-embellished example. (The
   `coverOneLiner`/tagline stays free to be descriptive — the fix is only for the **name**.)

4. **Fallback without invention.** If `lead.title` is empty: have Understand capture the **literal** project
   name from the brief (a new Intent field, e.g. `projectName`), else use the company name — never synthesize
   extra words.

### Files in scope
- `backend/src/modules/generation/blocks/block.types.ts` + `frontend/app/types/proposal.d.ts` — add
  `projectTitle` to `ProposalMeta`.
- `backend/src/modules/generation/generation.service.ts` — `buildEngineInput`: set `meta.projectTitle = lead.title`.
- `backend/src/modules/generation/engine/engine.service.ts` — assemble cover (use title), compose prompt
  (no-invention wording + example), fallback chain.
- (Optional) `backend/src/modules/generation/engine/understand.service.ts` + `intent.types.ts` — literal
  `projectName` extraction as a last-resort fallback.

### Verification (when implemented)
- Lead titled "AP Invoice Automation (SAP)" → cover shows exactly "AP Invoice Automation (SAP)", not an
  embellished "AP Automation Digital Platform".
- A brief that names the project → the cover uses that exact name; no extra words are added.
